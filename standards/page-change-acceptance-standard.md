# 页面变更轻量验收标准（方案 C）

> **状态**：Accepted
>
> **适用范围**：所有前端页面、页面字段、按钮/路由及直接影响页面行为的 API/DTO 变更。
>
> **目标**：以最小必要成本在提交前发现明显缺陷，在部署后用精确影响面复验；提高一次部署成功率，不把普通改动升级成每次全量 E2E。

## 1. 核心决策

采用两段门禁：

1. **提交前本机主门**：最终 staged diff 对应的 build/typecheck、契约检查和真实浏览器定向验收。
2. **部署后 CI 二次门**：绑定 exact SHA 执行 `floor + 本次改动页面 + 直接关联页面`。

本机验收负责尽早发现字段、入口、DTO、保存和回显问题；CI 负责发现候选包、部署配置、网关、权限和集成环境差异。两者职责不同，不能互相替代。周期性全量巡检独立运行，不进入普通提交关键路径。

## 2. 触发边界

以下任一项变化即触发：

- 列表列、查询条件、详情展示、新增/编辑表单、下拉、上传、默认值、必填/值域；
- 页面按钮、行操作、菜单、路由、来源单据、跨页面跳转；
- 页面真实使用的请求/响应 DTO、校验、映射、投影、持久化或权限；
- 共享组件、请求层、路由或菜单配置影响一个或多个页面消费者。

仅文案或样式且已证明不影响绑定、提交、路由与行为时，可不跑业务 UI，但仍完成对应静态检查。不能按“文件少”“只改前端”“DTO 本轮未改”豁免。

## 3. 编码前影响矩阵

在当前任务记录追加紧凑矩阵，不另造重复文档：

| 变更字段/操作 | 来源入口 | 实际受影响页/消费者 | 数据与操作链 | 本机场景 | CI模块 | 状态 |
|---|---|---|---|---|---|---|
| 字段、按钮或路由及前后含义 | 菜单、列表、详情、关联单据 | 列表/详情/新增/编辑及真实兄弟入口 | UI -> DTO -> 校验/Service -> DB -> DTO -> UI | 正向、回读、反例 | `@module:*` | covered/pending/blocked/approved-defer |

最低要求：

- 字段变更检查所有真实存在的列表、详情、新增、编辑、关联选择、导入导出消费者；不存在的页面不虚构。
- 新增入口时同时检查来源页和目标页。例如“采购申请详情发起询价”与“询价新增选择采购申请”是两个独立入口，必须分别验收。
- 按钮/路由核对当前记录 ID、业务类型、path/query、权限、后端动词和目标对象，不以字符串存在代替可达性。
- 共享层影响未知时，影响面计算必须失败并补映射；禁止缩成 floor-only。

## 4. 真实数据策略

验收数据在编码初期确认，不能留到部署后碰运气：

1. 优先使用字段完整、状态正确的现行记录。
2. 没有合适数据时，使用真实物料、组织、供应商等主数据新建唯一业务单据；唯一键推荐 `ci-<run>-<attempt>` 或同等不可碰撞规则。
3. 草稿和安全可逆数据在场景结束后清理；不能清理的发布态数据必须唯一、可追踪并登记。
4. 测试环境脏历史数据可在确认目标与影响后修复或删除；不得为让测试变绿而广泛清库。生产删除仍执行生产授权规则。
5. 历史兼容属于需求时，另建明确命名的历史回归；否则不让脏历史数据成为唯一 happy path。
6. 账号使用固定最小权限池，不在每次作业临时创建。写入型场景每作业独占账号；只对相同共享业务资源加模块锁。

## 5. 本机提交前主门

本机门必须对应最终候选，而不是开发中间态：

- 先执行受影响仓 build/typecheck、现有契约/映射/路由测试。
- 使用仓库 Playwright CLI headless 跑最小代表集；每个改动入口/关键页面为独立场景。
- 字段变更至少证明：真实数据加载、真实 UI 提交、后端持久化、编辑或详情再次读取、缺失/非法/依赖失败中的一个适用反例。
- 天然 `1:N` 的多物料业务单据发生明细字段或操作变化时，使用真实 UI 覆盖受影响的添加、编辑、删除及适用导入；保存后重新读取并核对明细数量、稳定标识和每行关键字段。仅一条明细、接口 200 或前端表格内存值不能证明多行契约完成。
- 下拉证明数据源、搜索/分页、`value/label`、关联 ID、回填及上游清空/重选。
- 页面断言业务主键、标题、关键字段、状态、关联对象及数量；扫描 `undefined/null/[object Object]/NaN/Invalid Date` 和裸 i18n key。
- 有 staged-diff 指纹 guard 时，先 stage 最终相关文件，再由 guard 运行/记录证据；staged diff 变化后旧证据失效。

可复用机械门位于 [`templates/hooks/page-change-e2e-guard.js`](../templates/hooks/page-change-e2e-guard.js)。项目接入时把它放在稳定路径，并让 `.git/hooks/pre-commit` 执行：

```bash
node <guard-path>/page-change-e2e-guard.js check --repo-path <frontend-repo>
```

验收人先 stage 最终相关文件，再通过 `record --repo-path ... -- <项目定向E2E命令>`生成本地证据。模板只验证“证据与 staged diff 同指纹且命令实际成功”，受影响入口清单及 E2E 命令仍由项目的影响映射和任务记录决定；禁止给模板硬编码某个业务仓账号、URL 或模块。

阻断条件：只有 API 200、页面打开、控件可见、测试替身、截图或 build 绿；未证明保存回读；入口之一未验；真实数据/账号/环境不可用但仍声称通过。

## 6. 部署后 CI 二次门

CI 绑定 exact SHA，部署后执行：

```text
L0 floor + affected modules + direct associated modules
```

- 页面 spec 使用稳定 `@module:<name>`；共享文件通过显式影响映射展开消费者。
- CI 默认使用固定账号池。只读任务可按账号槽并行；写任务使用独立账号、唯一数据和资源标签，如 `@write @resource:inquiry`。
- 同一共享资源串行；不同模块可并行。数据库迁移、APISIX 和共享基础配置继续全局串行。
- 证据至少包括候选 SHA、环境、账号角色、业务键、模块选择、测试结果和失败制品。
- CI 是本机门后的二次兜底；不得以 CI 将来会跑为由提交未在本机验收的页面变更。

## 7. 成本控制

轻量不等于少验，含义是按影响面验：

- 普通页面改动不跑全菜单；只跑 floor、变更入口和直接兄弟入口。
- API 级 setup 可用于准备数据，但页面保存验收必须由真实 UI 发出请求。
- 独立页面拆独立场景，可并行时并行；写入资源只锁相同模块，不使用全局 E2E 大锁。
- 依赖只缓存下载层：NuGet packages、npm cache、pnpm store；不缓存 `node_modules`、build/dist、浏览器目录和测试结果。
- 失败只重跑受影响检查；候选、依赖、环境或 staged diff 变化时，相关证据必须重建。

## 8. 完成定义

页面批次只有在以下项全部满足时才能标 `complete`：

- 影响矩阵无未说明的入口、字段链或消费者；
- 本机 staged-diff 门通过；
- exact SHA 已部署且 CI 定向门通过；
- 正向保存重读、适用反例及错误反馈有真实证据；
- 创建数据、清理状态和所有 `pending/blocked/approved-defer` 已记录；
- 提交、远端、制品和运行版本按项目发布规则一致。

## 9. 与既有标准的关系

- 字段/DTO/消费者深度要求来自 [ADR-008](../decisions/ADR-008-end-to-end-8-checks.md)。
- CI 影响面和分层执行来自 [CI/CD E2E 标准](cicd-e2e-in-pipeline-standard.md)及 ADR-045。
- 页面结构和交互外观仍执行 [Frontend UI V2](frontend-ui-v2-standard.md)。
- 本标准提供日常页面改动的轻量执行组合，不削弱鉴权、迁移、DB、生产和项目现场门。
