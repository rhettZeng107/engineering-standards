# Frontend UI V2（Atlas）标准

> 状态：正式。适用于 React 18、antd 5 与 `@ant-design/pro-components` 项目。
> 本文只规定 V2 的强制边界；列表交互细则直接引用
> [`frontend-ui-standard.md`](frontend-ui-standard.md) 与
> [`react-ui-guidelines.md`](react-ui-guidelines.md)，不在三份文档中重复维护。
> 共享组件真理源：`references/v2-components/`。

## 1. 适用原则

- 本标准是所有前端页面编码的强制基线，不区分简单轨、标准轨、迁移轨或其他任务类型。新增、修改、重构和迁移页面必须在同一交付批次按 V2 落盘并验收；不得因改动小、沿用旧页面、只改字段/按钮/接口或计划后续美化而豁免。
- 页面必须先判定为列表页、独立业务路由页、短事务 Modal 或看板/报表，再套对应范式；不得用 V2 页头、颜色或卡片替代完整页面范式。
- 业务字段、按钮、校验、请求和保存契约不得因布局升级被删减。真实保存、持久化、回显和失败路径仍按项目验收标准执行。

## 2. Token 与基础组件

- 入口统一引入 `v2-tokens.css`，并将品牌色、语义色、圆角、画布、文字和字体映射到 antd `ConfigProvider`；页面不得硬编码主题色。
- 新增或修改的页面须使用同一套语义 token 覆盖浅色与深色：画布、容器、浮层、表头、边框、主次文字、焦点、链接及状态色均随主题变化。产品可保留自己的品牌主色；业务状态色按含义选用，不把品牌色当成全部成功色。支持主题切换的宿主须让已打开的子应用同步实际主题，未接入的子应用不得计为全站双主题完成。
- 宿主侧栏、菜单分组、搜索、账户区、顶栏与首页工作台须跟随实际主题；浅色模式使用浅色导航工作面与深色文字，深色模式使用深色导航工作面与浅色文字。工作台欢迎区、卡片、状态和应用图标均使用主题 token。当前页签对应的左侧菜单须持续显示选中底纹，点击其他菜单或切回已打开页签时同步切换；品牌色用于选中、焦点和动作，不把侧栏固定为深蓝色。
- 主动作、状态与风险操作按下表分别判断。`新增`只表示创建，不能自动推断为安全；例如「加入黑名单」虽有“加入”动词，仍是限制供应商资格的危险操作。操作列不得用无业务含义的多色按钮。

| 角色 | 适用行为或状态 | 浅色 / 深色表达 | 交互要求 |
|---|---|---|---|
| 主动作 | 新增普通档案、查询、保存、确认配置 | 青绿实心按钮；深色使用亮青绿底配深字 | 同一区域只突出主要下一步；禁用态保留原因 |
| 普通动作 | 查看、编辑、导出、返回、刷新 | 中性按钮或青绿文字链接 | 操作列用文字说明动作，图标按钮提供名称和焦点 |
| 需关注 | 待复核、临期、缺资料、尚未保存 | 琥珀文字、底色或提示边；不作为默认“提交”按钮色 | 写出风险及下一步，不能只靠颜色 |
| 危险动作 | 删除、作废、驳回、移出受控范围、加入黑名单等限制性变更 | 红色 `danger` 按钮或链接；深色红底配深字 | 标明作用对象、二次确认，成功后刷新或回读 |
| 结果状态 | 可用/通过、处理中、风险、阻断、历史中性 | 青绿、信息蓝、琥珀、红、灰的文字＋浅/深底色 | 不同业务维度分列，状态同时显示文字与点或图形 |

色值由产品 token 与 antd `ConfigProvider` 提供；浅色参考青绿 `#0b726b`、深表头 `#174653`，深色参考亮青绿 `#56c4b7`、表头 `#34464a`。表头文字与排序、筛选图形在两种主题下都须可读；危险、成功、风险色不按字面动词套用。正文与底色至少 4.5:1，重要图形和控件边界至少 3:1；悬停、选中和禁用状态分别检查。
- 业务页复用 `SectionCard`、`StepAnchorNav`、`InlineDetailTable` 和 `V2States`；禁止自造同职能组件或用空卡片冒充业务分区。

设计效果对照：列表页[白天](../references/ui-v2-theme-examples/list-light.png)／[夜晚](../references/ui-v2-theme-examples/list-dark.png)，参数页[白天](../references/ui-v2-theme-examples/settings-light.png)／[夜晚](../references/ui-v2-theme-examples/settings-dark.png)。HTML 可切换主题并查看窄屏排布；示例数据不代表任何业务契约。

## 3. 列表页（强制）

列表页的定义、布局和交互以
[`frontend-ui-standard.md`](frontend-ui-standard.md) 与
[`react-ui-guidelines.md`](react-ui-guidelines.md) 为唯一细则来源，并至少满足：

1. 使用 `ListPage` 四段式：标题与主操作、可选快捷筛选、字段过滤与工具栏、表格与分页。不得用多层 `Card`、手写搜索条或页面级 `Spin` 替代该结构。
2. 主表使用 `ProTable` 或项目自包含的 `AutoHeightProTable`。查询条件声明在 `columns`，使用字段级、带标签的过滤控件；`search.labelWidth="auto"`，提供重置、查询及适用的展开/收起。
3. 显式保留刷新、密度和列设置三图标。`toolBarRender={() => []}`，不得设为 `false`；列设置须支持显隐和拖拽排序，宽表按业务需要支持固定列。
4. 每列声明稳定 `width`；编号、时间、状态等常用列保持一致口径。操作列固定在右侧、宽度统一，查看/编辑/删除及状态动作的顺序和危险色遵循 React 列表标准。
5. 新增、导入、批量操作等页面级动作放在 `ListPage.Title.extra`；不得挤入 ProTable 内部工具栏。空、错、加载使用 `V2States`，接口异常不得伪装成空数据。
6. 列表视觉顺序为「标题/说明 → 带标签的字段筛选及右侧重置、查询 → 左侧结果数/排序说明与右侧刷新、密度、列设置 → 表头/数据/分页」。宽屏常用筛选项可排四列，窄屏依次收为两列、一列；三个工具按钮桌面统一 36×36px 边框盒，触控视口不小于 44×44px，图形约 16×16px 且居中，不得出现小图标配大空框或受裁切、变形的图形；同时须有可辨识名称、提示和键盘焦点。视觉示例见[明暗列表页](../references/ui-v2-theme-examples/list.html)，交互与响应式细则以列表标准为准。
7. 表格表头使用深青绿工作层和高对比文字，排序、固定列、筛选图形的普通、悬停与选中状态一起适配；行内普通编辑用青绿文字，危险操作用红色文字并确认。具体品牌色可映射，不得把浅色表头或状态色硬编码到深色主题。

普通 antd `Table` 只适用于看板内部摘要表、表单明细表或无分页/无 CRUD 工具栏的非列表型局部表格；不得用于规避列表页标准。

## 4. 新增、编辑、详情与流程页（强制）

- 原 Drawer 或宽 Modal 中的新增、编辑、详情、主从和流程业务，统一改为 Main/门户框架内的子应用路由独立页。列表通过 `navigate(route)` 进入，页面按 route id 重新取数，支持刷新和深链。
- 独立页使用画布背景，利用 Main 可用宽度，左右安全边距 5–15px；顶部包含面包屑、标题、说明和右上角操作区，主体按业务分组使用 `SectionCard`，长页面按需使用 `StepAnchorNav`。
- 新增页右上角为 `[返回][保存]`；编辑页为 `[返回][删除][保存]`；详情页为 `[返回]+已授权业务动作`。返回采用 `navigate(-1)` 或明确来源路由；不得同时提供同义“返回”和“关闭”。
- 保存成功返回来源列表并触发刷新；未保存返回、并发冲突、加载错误和无权限必须有明确反馈。不得只依赖 Drawer 内存或 `location.state` 维持页面数据。
- 确认、提示、导入以及无明细且不超过 10 个字段的短事务可保留普通 Modal；不得把覆盖式全屏 Modal 当作独立页。
- 单页面参数配置属于独立业务路由页。按配置范围、平面薄边界的业务分区、影响预览、修改原因及统一保存组织；不以多层圆角卡片堆砌。长页面显示未保存状态和当前影响，未保存用琥珀、已保存用青绿、保存失败用红色文字与反馈；保存失败保留输入并定位错误。实际字段、权限、生效时点与历史快照由所属业务契约决定。明暗布局示例见[参数页](../references/ui-v2-theme-examples/settings.html)。

## 5. 业务单据多物料明细（强制）

- 询价单、采购申请、采购订单、发货计划、发货单等业务，只要领域模型天然允许“一张主单对应多条同构物料明细”，新增和编辑页就必须使用 `InlineDetailTable` 维护明细，一行对应一条物料业务记录。触发条件是单据的 `1:N` 契约，不是用户是否从列表批量选择物料，也不取决于当前实际只有一条还是多条明细。
- 当前只有一条物料时仍沿用同一明细表结构并保留继续添加能力；不得退化为单物料长表单，也不得预生成多条空白记录模拟固定行数。详情页沿用新增/编辑页相同的字段语义、列顺序和行粒度，以只读明细表展示，不另造卡片式或摘要式替代结构。
- 禁止把每条物料渲染成纵向堆叠的“行项目卡片”或重复表单块，尤其不得为每条明细重复标题、删除区、说明/提示框和整组公共字段。物料编码、描述、数量、单位、交期等可比较公共字段必须成为表格列；类别、科目分配等少量条件字段通过动态列、单行展开，或“当前选中行”的单一辅助编辑区承载，不得一次展开 N 套大表单。
- 明细表置于业务单据独立路由页的 `SectionCard` 分区内，不替代顶层 `ListPage + ProTable` 资源列表。每行使用稳定业务明细 ID；新增未保存行使用稳定临时 key。物料选择必须保留契约要求的 ID、编码和名称，品牌、类型、单位、数量、税务、交期、附件等列及联动以真实业务最大字段集为准，不得为压缩表格删减契约。
- 新增、编辑默认提供添加和删除行；复制行、模板下载和批量导入按业务场景启用。导入使用 `ImportModal`，行附件使用 `FileUploader`。重复物料是否允许、默认税务/单位/交期、删除既有明细的语义及部分接收策略必须由业务契约决定，禁止前端猜测或静默覆盖。
- 必填、值域、字段联动和异步校验落实到具体行与单元格；提交失败须定位首个错误行并保留用户已录入内容。不得静默丢弃不完整行或只提示笼统“保存失败”。主单与明细作为一次业务保存处理；除非契约明确支持并逐行展示部分成功，否则任一明细失败不得反馈整单成功。
- 保存验收必须使用真实数据证明“主单 + 多条明细”持久化，并在编辑页或详情页重新读取后核对明细数量、稳定标识和关键字段。只验证单行、接口 200、表格渲染或前端内存值，不能证明多物料单据完成。
- 每列声明稳定宽度；物料和操作列按需固定，宽表提供明确横向滚动。桌面与适用移动端在 100%、125%、150% 缩放下不得截断操作或压缩到不可读；窄屏可采用横向滚动、单行展开或当前选中行辅助编辑区，但不得改回多卡片堆叠，也不得改变字段集和一行一明细的业务语义。

## 6. 上传与导入（强制）

- 所有附件上传统一使用 `FileUploader`，所有 Excel/批量导入统一使用 `ImportModal`；底层必须是 antd `Upload.Dragger`，同时支持拖拽和点选。
- 禁止裸 `<input type="file">`、只点选的 plain `<Upload>` 或页面自造上传器。组件必须覆盖文件类型、大小、数量、上传状态、删除、下载/预览和错误反馈。
- `FileUploader` 按场景使用 `action`、`defer` 或 `base64` 数据流；受控值必须在顶层保留 `fileId`。`ImportModal` 必须提供模板、上传、解析/预览、逐行错误和成功后的刷新语义。

## 7. 验收门

- 静态检查：列表页具有 `ListPage`、`ProTable` 字段过滤、三图标和统一操作列；业务 Drawer/宽 Modal 为独立路由；天然 `1:N` 物料单据使用 `InlineDetailTable` 且详情保持同构只读列，不存在按物料重复渲染的大卡片/整组表单；上传入口只使用统一 Dragger 组件。
- 行为检查：从真实门户菜单进入；查询/重置/分页/列设置、CRUD、返回、刷新恢复、上传成功和失败均可操作；多物料单据覆盖添加、编辑、删除及适用的导入/附件，并完成整单保存回读；关键列使用真实数据且不为空或 `-`。
- 视觉检查：桌面及适用移动端在 100%、125%、150% 缩放下无重叠、截断和无效大留白；固定列、横向滚动和操作区可用。列表三工具在真实浏览器中分别核对桌面 36×36px、触控视口至少 44×44px 的边框盒、约 16×16px 的居中图形和刷新、密度、列设置原有功能。
- 主题检查：浅色、深色及跟随系统的实际画面均核对宿主侧栏、菜单选中态、搜索、账户区、首页工作台、画布、表格、表单、弹窗、通知和状态徽章；浅色导航须为浅色工作面，深色导航须为深色工作面。切换不清除查询或未保存输入，不刷新已打开的子应用页签。正文与背景对比度至少 4.5:1，状态文字、图标、边界至少 3:1；颜色以外仍有文字或图形语义。
- 工程检查：build/test 通过，外网字体请求为零，主题 token 无页面级硬编码。任一适用项未覆盖时，页面不得标记为 UI V2 完成。

## 8. 工作流要求

- AI UI 能力按职责分层：`frontend-design`负责页面创作与设计方向，`frontend-quality-gate`负责基于源码、渲染结果和项目规范的证据化审查；`impeccable`仅作为显式调用的补充工具，用于确定性检测或可信本地环境的可选 Live Mode。不得用任一技能的审美偏好覆盖本标准、项目设计系统和业务契约，也不得把检测无告警当作真实 UI、可访问性或业务验收通过。
- `impeccable`默认关闭隐式触发、自动 Hook 和遥测；确定性检测先作为人工审查证据，不直接成为 CI 阻断条件。Live Mode 只允许在用户明确要求后操作可信本地源码与开发服务器，不得为其放宽生产 CSP、浏览器安全或部署边界。
- 任一任务轨只要涉及页面编码，编码前必须登记受影响页面及 `pageType`，编码中实施对应 V2 条款，批次验收提供页面级静态证据和真实 UI 行为证据。任一适用项未通过，页面与批次不得标记完成。
- 后续每个接入门户的子应用按其实际页面矩阵逐页实施本文与引用的列表标准：在子应用内使用主题 token 渲染明暗两套页面，从真实门户入口核对主题同步、列表工具和状态语义；只修改门户外壳或共享样式，不能代替子应用页面代码及业务行为的验收。
- 日常页面变更按[页面变更轻量验收标准](page-change-acceptance-standard.md)执行“最终 staged diff 本机主门 + exact SHA 部署后 CI 二次门”；按影响面验收不等于省略入口、保存回读或兄弟消费者，也不要求每次跑全菜单。
- 迁移项目额外把“源功能等价”和“目标 UI V2 符合性”作为同一迁移单元的两个并列合同：源页面清单保证不漏业务，本文及其列表细则保证目标形态。两者同批编码、同批提交、同批 E2E；任何一项未通过，迁移状态只能是 `partial`、`pending` 或 `blocked`，不得记为 `complete`。
