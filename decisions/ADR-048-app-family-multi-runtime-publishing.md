# ADR-048: 应用家族单身份多运行时发布

- **Status**: Accepted
- **Date**: 2026-07-14
- **Decider**: 涛哥
- **Scope**: 跨项目 / BP、应用中心与多模块子应用

## Context(背景 / 为什么需要决策)

APS 的计划排程与库存分析有独立虚拟目录和独立后端，但业务上属于同一个 APS 应用家族。若按部署单元拆成两个 `SYS_SubApp`，门户会出现重复根、授权身份分裂，5041/5042 的业务责任也更容易串线。反过来，如果仅因业务名称接近就强行合并，又会混淆授权、审计、租户和合规边界。

2026-07-14 完成实现与初验，2026-07-15 功能 E2E 复验确认：BP 可用一个 `AppName=aps`、一个原子聚合 manifest 管理“计划排程”和“库存分析”两个一级模块，同时让 `/aps` 与 `/aps-inventory` 分别访问 5041、5042；BP 9999 组织计划四页与库存物料链路均为 200。该证据验证多运行时发布 happy-path，不代替 ADR-047 的全协议异常矩阵。

## Decision(决策本身)

**一句话**：应用身份按业务治理边界划分；同一应用家族使用单一 AppName 和原子聚合 manifest，各模块可独立运行、部署和回滚。

**详细**:

- 只有授权命名空间、审计责任主体、租户/组织语义、业务负责人及生命周期、合规分级全部一致时，模块才可合并为一个应用家族。任一边界不同，即使业务相关也必须拆成独立 `AppName`；仅独立发布不构成拆分理由。
- 一个业务家族只登记一个稳定 `AppName`、一个 active `SYS_SubApp` 和一个门户根。独立模块可拥有各自虚拟目录与业务后端，BP 按 AuthTag/运行时映射路由。
- 应用中心只消费一个聚合 manifest。组件 manifest 是内部输入；组件不可用、AppName 不一致、菜单为空或 AuthTag 冲突时聚合端返回 503，不发布半份菜单。聚合器不代理组件业务 API。
- 组件 manifest、聚合器和 BP 运行时映射必须兼容当前版 N 与上一版 N-1。
- 正向发布：组件后端/虚拟目录 → 聚合 manifest → BP 运行时映射 → SYS 扫描/重发布/上线 → 按既有家族权限补新模块授权 → 真实 BP iframe E2E。
- 回滚：停止新扫描/发布 → 恢复上一版菜单快照或重发 N-1 manifest → 恢复 BP N-1 运行时映射 → 回退聚合器 → 回退组件。任一步失败都不得让半份菜单继续在线。

## Consequences(影响 / 副作用)

### 正向

- 多后端应用保持统一菜单、授权和审计身份，同时保留独立部署与回滚能力。
- 门户用户只看到一个稳定应用根，不因技术拓扑重复授权。
- fail-closed 聚合器避免菜单只发布一半。

### 负向 / 代价

- 聚合 manifest 成为发布闸门；任一组件失败会阻断整个应用家族的新菜单发布。
- BP 必须维护 AuthTag 到运行时的映射，tab/registry identity 也必须包含真实运行时路径。
- 统一 AppName 不代表业务数据已经统一；各后端仍须分别完成多租户隔离和细粒度授权。

## Alternatives Considered(其他选项 + 为什么没选)

### A. 每个部署单元登记一个子应用

- 优点：注册和部署一一对应。
- 缺点：同一治理边界出现重复门户根、AppName 和授权集合。
- 不选原因：部署拓扑不应决定业务身份。

### B. 由主后端反向代理其他模块业务 API

- 优点：浏览器只看到一个后端地址。
- 缺点：主后端承担其他模块的故障、容量和安全责任，独立回滚失真。
- 不选原因：聚合菜单不等于聚合业务流量。

### C. 单身份 + 聚合 manifest + 独立运行时(选)

- 优点：治理身份统一，部署和业务流量仍可独立。
- 缺点：需要聚合门禁、运行时映射和 N/N-1 回滚协同。
- 选定原因：APS 双后端已经完成真实门户验证。
