# ADR-038: 子应用主数据消费 API、不直查共享表;业务各自重建(应用独立性原则)

- **状态 / Status**: Accepted
- **日期 / Date**: 2026-06-15
- **决策者 / Deciders**: 涛哥(拍板)+ Claude(提议)
- **影响范围 / Scope**: 全族业务子应用 —— SYSV2 / MDM / SRMV2 / MESV1 / TPM / 未来 WMS / EAM 等;凡涉及人员/岗位/物料等主数据的读取与跨子应用业务重建
- **关联 / Relates**: ADR-012(子应用 onboarding SOP)、ADR-037(跨栈契约锁)、ADR-014(迁移轨)

## 背景 / Context

业务子应用(TPM/SRM/MES/WMS/EAM …)与 SYS/MDM 共享同一组数据库(如 `ExtendLibrary`),历史做法常**直查共享主数据表**(如 `BaseEmp`/`BaseHRInterfaceView`/`HrPosition`/`MDM_Labels`/`SYS_Organization`)以取人员/岗位/物料。

直查共享表的实证问题:
- **耦合主数据物理 schema**:主数据表结构变更(列名/视图/口径)直接打穿所有直查的子应用,改一处牵全身。
- **职责越界 / 双写风险**:子应用直写他方主数据表(如业务子应用写 `SYS_Organization`),与主数据 owner(SYS 控制台)形成双写,一致性失控。
- **绑死同库部署**:直查假设"同库可达",一旦主数据库拆分/独立部署即断;违背子应用独立发布(各子应用发布到 BP 门户独立运行)的目标。
- **无统一过滤/鉴权/审计**:工厂隔离、权限、脱敏散落在各子应用的直查 SQL 里,口径不一。

实证锚点(2026-06-15 TPM 设备组织迁移会话):EAM 设备组织那套 Organization/* 后端在老 SysWebApi(FW),底层 `SYS_Organization*`/`BaseEmp` 与 SYSV2/MDM 共库;迁移评估中确认人员/岗位(SYS `HREmpController`/`HRPositionController`)、物料(MDM `LabelRelation`)均已有/应有独立 webapi 提供,无需各子应用各自直查。

## 决策 / Decision

**确立子应用独立性原则两条:**

1. **主数据消费 API,不直查共享表。**
   - 人员、岗位、物料(及同性质的组织/工厂/供应商等)**主数据**,由其 owner 子应用(SYS / MDM / HRIS)以**已发布 webapi** 提供(按工厂等维度过滤 + 鉴权)。
   - 消费方子应用经**后端 HttpClient**(对齐各仓既有外部客户端范式,如 `MesApi`/`MdmApi`/`SysApi` + `ITokenProvider`)调用,**前端只调自己后端**;**禁止直查他方主数据物理表/视图**。
   - owner 子应用负责维护 API 契约稳定 + 字段口径单源。

2. **业务在各自子应用重建,不跨应用直接复用后端。**
   - 非主数据的业务能力(业务实体 CRUD、关系挂载、状态机、业务编排)在**使用它的子应用内重建**,即使老系统是另一处实现。
   - 业务子应用可拥有"业务关系表"(如挂载/分管关系),但其引用的主数据键来自消费的 API,不反向让主数据 owner 依赖业务表。

**目的 = 应用独立性**:主数据单一 owner + API 边界,使每个子应用可独立开发、测试、发布、演进,降低共库耦合与双写风险。

### 适用与例外
- **适用**:新建 / 迁移 / 重构子应用涉及人员/岗位/物料等主数据读取时,默认走 API。
- **历史代码**:已直查共享表的存量代码按"后续逐步收敛"处理(本 ADR 是"后续统一原则",不强制即时全量重构历史;新增/改动命中即按本 ADR);列入各项目 backlog。
- **真例外**(需 Tier 3 拍板 + 记录):API 不可得且主数据 owner 短期不提供、性能极端场景经实证 API 不可行 —— 直查须 owner 授权 + 标注 + 限只读 + 工厂隔离不破。

## 替代方案 / Alternatives

| 方案 | 否决理由 |
|---|---|
| 维持直查共享表 | 耦合 schema + 双写风险 + 绑死同库,违背独立发布目标 |
| 跨子应用直接引用对方后端程序集/Service | 编译期强耦合,失去独立发布/演进;subagent/团队边界也对不上 |
| 主数据复制一份到各子应用本地表 + 同步 | 多副本一致性债 + 同步基建成本,主数据应单源 |

## 影响 / Consequences

- **正向**:主数据单源(owner 维护 API 口径);子应用解耦、可独立发布;工厂过滤/鉴权/审计集中在 owner API;schema 变更影响面收敛到 API 契约。
- **成本**:owner 子应用需补/维护对外 webapi;消费方需建 HttpClient + 处理跨子应用鉴权(token 透传)+ 网络失败兜底;比直查多一跳。
- **配套**:
  - 消费契约仍受 **ADR-037** 约束(跨栈契约锁:动词/路由/字段/大小写)。
  - 跨子应用调用鉴权按 BP 门户统一 SSO/token 范式。
  - 各项目 CLAUDE.md / memory 回链本 ADR;存量直查项进各项目 `backlog`。
- **首个落地**:TPM 设备组织迁移(`TPMV2/docs/superpowers/specs/2026-06-15-eam-organization-migration/`)—— 人员/岗位消费 SYS API,组织树/挂载/分管业务在 TPM 重建(参见 TPM `docs/decisions/ADR-005`)。

## 修订(2026-06-15)

**澄清「主数据消费 API」的适用判据 —— 不是所有挂"主数据"名号的对象都走 owner API。**

TPM 设备组织迁移实际落地时,"设备类别/设备类型"**未**走 MDM API,而是 TPM 子应用**自建/复用本应用内的分类实体**(`EquipmentCategory` 树 + 自建关系表 `TPM_OrganizationToCategory`)。原文背景示例曾把"物料/设备类别"一律归为"走 MDM API",过宽。修正判据:

- **走 owner API(决策 1)** 的前提是:该数据**确为他方 owner 的权威主数据**且 owner 已发布稳定 webapi(如 SYS 的人员/岗位)。
- 若某"分类/类型"**本就是使用方子应用的业务维度**(各应用对"设备类别"的口径/层级/扩展字段不同),则属决策 2「业务在各自子应用重建」——**子应用自建分类实体 + 关系表,不强行消费他方 API**,反而更独立。
- 判定顺序:先问"这是谁的权威主数据?"→ 是他方且有 API → 消费;是本应用业务维度 / 他方无稳定 API / 各应用口径不一 → 自建。

→ 人员/岗位(SYS 权威)= 消费 API;设备类别(TPM 业务维度)= 自建。两者都服务于"应用独立性"总原则,只是手段不同。
