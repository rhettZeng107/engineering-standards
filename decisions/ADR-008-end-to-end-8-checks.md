# ADR-008: 端到端交付 8 项核对清单(技术契约 4 + 业务连通 4)

- **Status**: Accepted
- **Date**: 2026-04-22 5 项升 8 项 → 2026-05-05 ADR 化回溯落地
- **Decider**: 涛哥
- **Scope**: 跨项目(全局规则)

> **执行阶段策略细化**(2026-05-14):8 项清单本身不变,但**分阶段执行** — Plan 落盘按 [ADR-024](ADR-024-plan-e2e-tiered-cicd-handover.md) 6 项硬冒烟,完整 8 项 + 跨浏览器 + 性能 + 跨页面回归由 CI/CD 接管。迁移轨(ADR-014)Plan E2E 双层保留。

---

## Context

### 触发场景

- 跨前后端 feature 验收漏点频繁:API 通了但前端调用错 / DTO 字段同步漏 / 业务操作闭环缺验证
- 早期"5 项核对"漏盖业务连通层(操作员实际能不能用)
- 实证:2026-04-22 升级为 8 项 — 在技术契约 4 项基础上加业务连通 4 项
- 实证:2026-05-04 涛哥反馈 E2E 主动业务约束实证防被动反应式踩坑(跑完整业务路径,不只 API 200 happy path)

### 决策不做的代价

- 验收靠"差不多对"经验判断 → 漏盖率高
- 操作员实操踩坑 → 涛哥被动反应式干预,Claude 反复返工
- 跨前后端 feature 没有统一验收基线 → 各 spec 重新定义验收

---

## Decision

**一句话**:跨前后端 feature 必做 **8 项核对**,任一不通 = 阻塞;技术契约 4 项 + 业务连通 4 项,不可裁剪。

### 技术契约层 4 项

① **API ↔ 前端调用双向核对** — 后端有的 endpoint 前端要么调用要么删除;前端调用的 endpoint 后端必须有
② **列表分页结构对齐** — `items` / `totalCount` / `current` / `pageSize` 字段名一致
③ **HTTP 动词 / 路由 / Policy 注册** — Policy 必须 `AddPolicy(...)`,否则抛 500
④ **字段契约一致** — 按实际请求/响应与业务规则对齐前端和DTO；页面隐藏字段不等于删除DTO/存储字段，DTO新增字段不等于每个页面都要展示；真删除或改名须覆盖全部实际消费者

### 业务连通层 4 项

⑤ **入口可达性全链** — 路由 → 菜单种子 → 权限码 → 登录看到 → 点进去渲染(整链不断)
  - ❌ **反模式**:把"前端 render-walk(直渲路由组件)/ URL 直达 / build 通过"当 ⑤ 已过 —— 缺菜单种子+权限码,**操作用户在菜单里根本看不到模块**。⑤ 必须在**有菜单种子 + 权限码 + 登录**的环境(部署/集成,非 dev)按操作用户视角验:菜单看得到 + 点得进。(2026-05-24 SRM 采购端补全踩坑)
  - **含义扩展(2026-06-12 修订,SRMShop 购物车入口复盘)**:⑤ 的"入口" = **菜单入口 + 应用内功能入口**(页内/壳层导航:加购后→购物车、列表→详情→下单等链路衔接点)。E2E 业务闭环用例**段间禁 goto 拼接** — 页面跳转必走真实 UI 入口(按钮/导航条/链接),goto 仅允许作用例起点;源系统壳层(layout)里的功能性入口在迁移中必须有去向(详 ADR-014 修订 2026-06-12 + legacy-migration-playbook §3.1 壳层枚举铁律/§5 坑 11)。
⑥ **Service 实装 + DB schema 对齐** — Controller 非空壳(实际查 DB 不返 mock 数据)+ EF 实体 vs `INFORMATION_SCHEMA.COLUMNS` 实证一致
⑦ **业务操作闭环 smoke** — CRUD + 日常交互(过滤 / 搜索 / 下拉 / 多选 / 联动,**每个用到的都验**)

  **交互后语义验收(修订 2026-08-30)**:⑦ 不是“按钮可点击”检查。每次打开详情、编辑、预览、查看明细或进入新路由后,必须等待目标视图稳定并断言:
  - 标题/主键可识别,且与发起行或接口对象一致;
  - 契约要求的关键字段、状态、关联对象真实渲染;实体存在时不得关键值全为 `-`/空;
  - 列表计数、汇总统计、Tab 数量与明细数据一致,空集合显示明确空态;
  - 页面不得出现 `undefined` / `null` / `[object Object]` / `NaN` / `Invalid Date` / 裸 i18n key或裸命令键;
  - API 2xx、无 console/pageerror、容器可见只是前置条件,不能单独宣称通过。

  批次中每个改动页面/关键详情必须是可独立运行的场景;单一前置用例失败不得遮蔽其他页面。缺少可验证数据时标记 `blocked`/未验,不得把壳层冒烟算作业务验收通过。
⑧ **错误反馈完整性** — toast / Modal / inline,无默默 500 用户无感

### 落地

- spec 验收段必显式列 8 项
- 主会话对受影响业务链执行8项核对；独立Reviewer仅按ADR-036当前规则调用，不把“已派评审”视为核对完成
- E2E spec 必盖业务连通 4 项(尤其 ⑦ 业务操作闭环)
- 跨子应用接入模板 `_template-app-onboarding.md` 强制 8 项

## 修订(2026-09-07)：页面字段与操作变更的影响闭环

**触发按业务影响，不按改动文件类型或数量**：精简/隐藏/删除/改名/变更必填、默认值、枚举、下拉、列表投影、查询字段、公共表单、按钮或路由，均先做字段级影响检查。仅改前端或仅改后端同样触发，不能因DTO本轮未修改而跳过。纯文案/布局且实证不影响绑定与行为可缩为对应检查。

**检查人**：默认主会话；用户点名独立Reviewer时，交付同一份影响范围与证据。检查的是最终变更造成的行为，必须读相关未改文件；不要把“仅评论新问题”误解为“只阅读diff文件”。

在已有spec/plan的验收表追加下表；小改可直接写在原任务记录，不另建一套文档。每个变更字段/操作一行；完全相同的数据链可成组但须列出字段名，不允许只写“MDM已检查”。

| 变更字段/操作及前后含义 | UI绑定与出入参 | 后端契约与实现 | 实际受影响页面/消费者 | 证据与状态 |
|---|---|---|---|---|
| 字段名；仅隐藏/真正删除/改名/必填或值域变化 | Form name、控件类型、初值/回填、submit mapper、响应读取；JSON实际key/type/null/缺省语义 | 请求/响应DTO、序列化、校验、Service/投影/映射、实体与DB契约 | 列表/详情/新建/编辑/查询/关联选择/导入导出；只列实际存在且引用该契约的兄弟页面 | 文件行/搜索范围/测试；covered、pending、blocked、approved-defer |
| 按钮/行操作及目标行为 | handler/Link、路由或API动词、记录ID/父ID/查询参数 | 路由注册/页面、endpoint/Policy、参数类型与返回结构 | 来源页面→目标页面/Drawer；菜单权限与操作角色 | 点击后目标标题、业务ID和字段语义证据及状态 |
| 页面联查/初始化/字段联动依赖 | 请求发起点、依赖字段、并行/顺序、取消/过期响应、加载与失败处理 | endpoint、参数、响应DTO、空集合/缺对象/错误语义 | 使用该依赖的全部当前页面区块/兄弟页面；退役字段遗留请求 | 依赖清单、失败传播、初次加载/重选/清空/回显/保存证据 |

逐项验证：

1. **显示变化与数据变化分开**。删控件后后端必填字段从何获得；编辑既有记录时，未显示字段是否被`undefined/null/0/空字符串`或表单默认值覆盖。区分不传、清空、保留；不得靠前端补假值满足DTO。数据是否保留必须用保存后重新读取证明。
2. **双向字段核对**。前端真实提交key与DTO/校验一致，响应字段须能在实际投影/映射和序列化结果找到；校验类型、大小写、可空性、日期、数字、枚举、id/name。下拉须验证option来源、value/label、选中回填、关联ID和保存含义；HTTP 200不证明字段值正确。
3. **消费者扩展检查**。用字段/DTO/endpoint/共享组件的语义引用或有边界的rg查找实际消费者，阅读关联未改文件；记录已影响、确认未影响及证据。不能因“DTO没改”“兄弟页面没在diff”“build绿”就豁免。公共DTO/投影/表单变更覆盖所有命中消费者，不泛化成整个仓库全量E2E。
4. **按钮与路由闭环**。核对生成目标、注册路由/组件、path/query参数、当前记录ID/业务类型、权限和后端动词；禁止只查字符串存在。真实UI从按钮到目标，断言目标对象、标题、关键字段/状态；用goto代替中间跳转不算通过。
5. **部署前验证分工**。先跑受影响仓的build/typecheck及现有契约/映射/路由测试；JS、cshtml、动态字段等不被类型覆盖的路径，用实际调用方/映射器的针对性测试补上。字段增删/必填/类型、下拉id/name、存量编辑保留和错误路由等已发生缺陷须有能复现旧错的回归用例，不写只断言代码字符串存在的镜像测试。
6. **页面完整依赖与生命周期**。枚举受影响页面当前的初始化、联查、字典、详情及保存前请求；逐个写明真实用途、依赖顺序和失败传播。删除/隐藏字段要追查旧请求、活动绑定、默认初始化、隐藏校验及保存payload是否仍存在；不能仅移除DOM。检查并行等待是否因非必要/退役接口失败阻断整页，loading是否在成功/空值/失败均能结束，异步对象未到时是否安全绑定，上游重选/清空是否重置下游且旧响应不覆盖新选择。
7. **回显与保存约束闭环**。按新建、存量编辑、只读详情及相关草稿/审批状态逐一核对：空对象/空集合/历史null、合法0/false、id与label、日期/数字/枚举、默认值、可编辑性、前后端必填与业务校验。核对读取DTO→表单回填→提交DTO→Service/实体保存→后续审批应用→再次读取全链；错误反馈须可见且不丢用户输入。对未展示/禁止编辑字段，验证保留策略；不得用`||`把合法0/false覆盖成默认值，不得用占位符掩盖关键回显失败。

**CR输出须有覆盖证据，不以PASS短语作结论**：列明基线/最终候选、全部受影响repo、当前依赖清单与字段/操作覆盖表、未覆盖项、运行过的检查与结果。静态契约矛盾/已知错误路由/必填遗漏直接回修；未验证不得算covered。真实UI至少覆盖每种受影响行为，修改字段必须检查新建（存在时）、存量编辑/回填、保存后重读；缺业务数据/环境则标blocked，不宣称业务通过。发布的前后端候选版本必须与验证记录一致；确因环境只能部署后验证时，明确该部署是待验测试部署，不将“包发布成功”当交付完成。

**验收优先级**：业务字段/数据保留/关联对象/按钮目标先于风格、命名和抽象建议。独立Reviewer的用途是对难判断的契约或风险提供反证；不能代替完整消费者清单、运行测试或真实页面验收。本修订覆盖下文旧的“同task同时改DTO与前端才触发”及按单字段豁免的说法。

## 修订(2026-05-25):①④ 前端↔DTO 对齐落地为「CR 主 + E2E 辅」双管可执行校验

**背景(实证)**:SRMV2 M03 迁移 E2E 双层(E2-a 入口可达 / E2-b 渲染+GET list 200 / E1 后端契约用 **spec 手写 payload**)实测发现 ①(API↔前端双向)+ ④(DTO 字段同步)**从未被真正执行** —— E1 打的是与 contract-lock 对齐的**合成 payload(非前端真实发出)**,E2-b 只验渲染+读路径连通、**不提交任何表单**。后果:前端表单字段名拼错 / 驼峰不符 / 漏发必填字段时,**三层全绿仍漏过**(批2 那 4 轮修复是同类,靠 E1 恰好跑了 create 才暴露,纯属运气;若是前端 payload 错则根本抓不到)。涛哥 2026-05-25 拍板 **A 双管**。

**决定**:①④ 不再是挂着的 checklist,落地为两道具体校验(**跨前后端契约改动 = 同 task 改 DTO / 接口 / 前端调用** 时强制):

- **CR 主 — 静态契约对齐(确定性 / 部署前拦截 / 零额外测试数据)**:比对**前端 service 层请求体字段 + 表单提交字段 + 响应字段读取** vs **后端 DTO 定义**(真理源 = contract-lock + DTO 类),检查:
  - (a) 前端发送的每个 key ∈ DTO 属性(防字段名拼错 / 驼峰不符)
  - (b) 后端校验的每个必填字段 ⊆ 前端实际发送(防漏发必填)
  - (c) 前端读取的每个响应字段 ∈ 后端响应投影(防读不存在的字段)
  - (d) 类型 / 格式对齐(日期、number vs string、枚举值域)
  - 归 code-reviewer「跨前后端」触发矩阵,作 E2E 前置门。
- **E2E 辅 — 动态真实表单(标准轨 CRUD 冒烟升级,详 [ADR-024](ADR-024-plan-e2e-tiered-cicd-handover.md) 同日修订)**:增删改至少 1 遍**走真实前端 UI 表单提交**(禁用 spec 合成 payload 替代),捕获真实出参断言 `payload ⊆ DTO + 必填齐 + isSuccess/2xx`;并断言列表至少 1 个已知 DTO 字段**真实渲染**(读路径字段映射,非仅「Table 可见」)。

**例外**:简单 task(单字段加列、配置)按 `feedback_skip_spec_plan_simple_tasks.md` 不强制双管;静态对齐可单独跑。**静态(CR)与动态(E2E)互补不互替** —— 静态抓命名 / 缺字段(便宜、早),动态抓运行期序列化 / 日期格式 / antd 表单 valuePropName(贴真实、晚)。

## 修订(2026-06-01)— ①④ 静态/动态校验以「契约锁文件」为基准

①④ CR 静态比对 + E2E 断言的真理源**统一为 Claude 本体产出的契约锁文件**(动词/路由/字段名/**大小写**/必填)。跨前后端契约**禁由 subagent 锁定**(context 隔离会传话失真,实证 HC camelCase 单会话栽 2 次),必须本体锁。详 [ADR-037](ADR-037-cross-stack-contract-lock-ownership.md)。

## Consequences

### 正向

- 验收基线刚性,漏盖率显著下降
- 操作员实操故障被防住
- 跨前后端 feature 工作量可预估
- code-reviewer / E2E / spec 三层都有 8 项核查点

### 负向 / 代价

- 每个跨前后端 feature 验收时间增加(8 项核对都要走)
- 简单 task(单字段加列)如严格走 8 项过度,故 memory `feedback_skip_spec_plan_simple_tasks.md` 已界定简单 task 跳流程

### 影响范围

- 全部 SYSV2 / HC / 后续项目跨前后端 feature
- memory `feedback_code_review_contract_check.md` / `feedback_e2e_proactive_business_constraint_check.md` / `feedback_upload_link_e2e_ui_layer.md` 同向
- 影响 spec / plan / E2E spec 编写规范
- 影响 code-reviewer 触发矩阵

## Alternatives Considered

### A. 全 E2E 自动化覆盖(不立人工核查清单)(已否)

- 优点:可重复 / 可 CI
- 缺点:8 项里业务连通层(⑤⑥⑦⑧)很多无法纯自动化,需人工核查;E2E 投入产出比在 SYSV2 阶段不划算
- 不选原因:E2E 是补充不是替代,人工 8 项核查仍必要

### B. 仅 API 契约 4 项(原 5 项的精简版)(已否)

- 优点:工作量小
- 缺点:漏业务连通层 → 操作员实操踩坑频繁
- 不选原因:实证 2026-04-22 5 项不够,升 8 项

### C. Case-by-case 验收(不立清单)(已否)

- 优点:灵活
- 缺点:每个 spec 重新定义,漏盖率高,新人 / Claude 无据可依
- 不选原因:实证多次踩同样的坑
