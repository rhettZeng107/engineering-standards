# ADR-028: 老项目迁移基线与两步走(三层等价 DoD + STEP1/STEP2 解耦)

- **Status**: Accepted
- **Date**: 2026-05-18
- **Decider**: 涛哥
- **Scope**: 跨项目(老项目迁移改造系列:SYS / MDM 已做 + SRM / MES / WMS / EAM / TPM 计划)

> **迁移轨决策两半**:本 ADR 管「**做什么算完**」(基线 + 三层等价 DoD + STEP1/2 解耦);「**怎么执行**」(Front-load / Back-automate / 中断纪律 / 完整性审计 workflow)见 [ADR-014](./ADR-014-migration-refactor-workflow.md)。**端到端操作主线(唯一总入口)= [legacy-migration-playbook §0](../standards/legacy-migration-playbook.md)。**

---

## Context(背景 / 为什么需要决策)

### 触发场景

2026-05-18 MDM 供应商主数据页踩坑复盘:迁移到今天才发现 `supplier/index.jsx` 一直是半成品 —— 列定义全错(物料列误标成供应商列、`dataIndex` 错位)。涛哥反馈迁移规则需固化:

> 老项目迁移,新基线 = 后端 .NET Core 8 + 前端 UI 工程标准;全部源工件(功能骨架/源页面)按新基线迁移;**先出一版新架构系统(STEP 1),再谈功能增强(STEP 2)**。

### 当前状态实证(本次 + 既往踩坑)

| # | 坑 | 实证锚点 |
|---|---|---|
| 1 | **工具链迁移冒充完整迁移** | MDM CRA→Vite(P3)只做 `process.env→import.meta.env` codemod,UI 工程标准 + 功能骨架未对齐 |
| 2 | **等价审查的半成品盲区** | `supplier/index.jsx` 在 `leibo` 源分支即半成品,等价比对「坏→坏」=「等价」直接放过 |
| 3 | **迁移未完成就做功能 → 逼出违规造新** | MDM 供应商双模式 v1 在 supplier 页仍半成品时做功能,未发现可复用骨架(`qualifiedsupplieredit` + `PostSupplier`),自造简版 Modal + `save` 接口 |
| 4 | **spec discuss 全局观不够宽** | grep 历史只 grep 概念/实体,未 grep「同模块已实现工作页作对齐标杆」 |

### 决策不做的代价

ADR-014 已定迁移改造轨工作流(Front-load + Back-automate),但**未定义「迁移完成」的判定标准**,也未约束「迁移 vs 功能演进」的先后。继续维持现状:半成品源页会持续蒙混过关;迁移未完成就压功能需求,反复逼出违规造新页面。

## Decision(决策本身)

**一句话**:老项目迁移按「STEP 1 基线迁移 → STEP 2 功能演进」两步走解耦;迁移完成以「三层等价 DoD」可度量判定;半成品源工件禁止等价搬运。

**详细**:

### 0. 迁移目标(总纲)

STEP 1 的目标 = **原业务在新基线上可正常使用**。这是 STEP 1 的**硬验收**,不是 STEP 2 再补 —— 否则迁移只是把异常 / 缺陷债务搬到新地基上继续累积。先保证原业务可用,才在新基线上谈 STEP 2 功能扩展。

### 1. 基线(Baseline)定义 —— 项目声明,不写死技术栈

基线 = 该迁移项目**启动时在 spec 声明**的目标构建栈、运行时、工程标准与**源仓分支范围**,不是某个固定工具。声明四项:
- **后端运行时**:目标 .NET / JVM / Node 等,按项目。
- **前端构建工具链**:目标构建工具(Vite / Rspack / Next.js / Webpack 等),按项目。
- **前端工程标准**:项目前端工程标准(SYSV2 前端统一 4 标准 ADR-023,或项目自有标准)。
- **源仓分支范围(2026-06-22 涛哥定,规则1)**:迁移源仓库基线**只取 `master` 与 `develop`**(二者并存按项目声明谁优先 —— 默认取功能更全者,如 TPM `develop > master`);**`customer/*` 等客户定制分支默认不作迁移源参考基线**(客户特化,不代表主线功能),**除非涛哥显式要求**纳入某客户分支。clone 后必 `git for-each-ref --sort=-committerdate refs/remotes` 列分支活动度核对主线为最新;若发现 `customer/*` 远新于 master/develop(暗示主线已停更、功能在客户线演进),**报涛哥拍板**是否改源,不擅自纳入、也不默认沿用停更主线。多版本仓(FW vs Core 等并存)选基线**必 diff 实证谁功能更全**,禁靠单点假设(踩坑:TPM 凭「FW 更全」假设选 FW,实测 net8 的 CORE 版活更久)。

**SYSV2 系列(SYS / MDM / SRM / MES / WMS / EAM / TPM)声明实例**:后端 .NET 8(三层 / 单层 WebApi 按既有架构)+ 前端 Vite + pnpm + antd 5 + pro-components + 前端统一 4 标准(ADR-023)。其他项目(如 HC)按自身技术栈声明,本 ADR 方法不挑栈。

### 2. 三层等价 DoD —— 缺一不算迁移完成
- ① **工具链等价**:迁到项目声明的目标构建栈 / 运行时(SYSV2 系列 = CRA→Vite、旧 .NET→.NET 8;HC 等其他项目按自身声明),`build` 0 error。
- ② **UI 工程标准等价**:套用项目声明的前端工程标准(SYSV2 系列 = 前端统一 4 标准、ListPage 四段式、ProTable 工具栏三图标,ADR-023)。
- ③ **功能骨架等价**:源页面的功能 / 字段 / 交互在新基线页面 1:1 可用;**以等价回归测试(老↔新行为比对)为强制证据**,不靠「应该能用」的假设。**老视图(cshtml/MVC Razor 等)源页必逐行提取「UI 功能清单」(每列/每按钮/每弹窗/每必填)** —— Claude 本体启动时提取并锁定作**契约锁基准**(ADR-037),贯穿全程:派单实现按清单逐项 1:1 等价落盘(边迁边对,避免返工)→ CR / E2E 验收对清单逐项打钩,任一项未勾即 ③ 不通过(2026-06-11 修订,详 playbook §3.2 UI 功能清单铁律)。

### 3. 源工件清单(Source Artifact Inventory)—— 迁移启动第一步
- 逐页 / 逐接口列「源工件 → 基线工件」对应表,每项标状态:`完好 / 半成品 / 坏`。
- **半成品 / 坏工件**:要么补完到基线、要么显式登记欠债 —— **禁止等价搬运**(半成品搬过来仍是半成品,等价审查抓不到)。

### 4. STEP1 / STEP2 两步走铁律
- **STEP 1 基线迁移**:全量源工件迁到基线,产出「新架构系统」。
- **STEP 2 功能演进**:基线迁移完成后的功能增强 / 优化。
- STEP 1 未完成的模块,**禁止** STEP 2 功能开发(防「在半成品上盖功能」)。
- STEP 1 **按模块切片验收**,非全系统一刀切 —— 某模块三层等价达标 → 该模块解锁 STEP 2。

### 5. 迁移轨默认增强、禁造新
- 迁移轨默认在现有页面 / 组件上增强(Extend);禁止新建页面 / 组件,除非实证「现有骨架确无可承载页」并经涛哥拍板。
- 落盘若新建 page / 组件文件 = 卡点,plan / commit 必须写明「为何不能在现有页增强」。

### 6. 迁移 = 移植,不是重写
- 迁移 = 把业务逻辑(`.cs` 实体 / Controller / Service、前端字段 / API 调用 / 表单逻辑)**移植(port)到新基线 + 适配**,业务规则原样保留。
- **禁止从零重写(rewrite)** —— 重写会丢老系统多年积累的边界处理与隐藏修复(本次 v1 简版 Modal 即重写恶果)。
- 真业务地基 = DB schema + API 契约 + 鉴权 + 数据;工具链(CRA→Vite)与运行时(.NET 8)对业务透明 —— 只要这四样不破,换工具链 / 运行时业务照常。
- **已上线系统迁移**(如 MDM 景颜生产):并行运行 + 等价验证通过后切换,不直接覆盖。

## Consequences(影响 / 副作用)

### 正向
- 「迁移完成」可度量,半成品源页无法靠等价审查蒙混。
- 迁移与功能演进解耦,杜绝「在半成品上盖功能 → 逼出违规造新」。
- 模块级切片解锁,STEP 1 不必全系统一刀切,避免周期失控。

### 负向 / 代价
- 源工件清单 + 半成品识别是前期额外工作量。
- STEP 1 期间功能需求需排队,产品节奏受约束。

### 影响范围
- 影响 ADR:ADR-014(迁移改造轨工作流,本 ADR 补「迁移完成」判定与两步走,互补不冲突)、ADR-016(grep 清单增补「同模块工作页」)。
- 影响 standards:新建 `standards/legacy-migration-playbook.md`(老项目迁移改造手册)。
- 影响 memory:`feedback_migration_enhance_existing_no_new_pages`(锚点本 ADR)。

## Alternatives Considered(其他选项 + 为什么没选)

### A. 维持 ADR-014 现状,不补「迁移完成」定义
- 优点:无额外规则。
- 缺点:半成品盲区不解决,踩坑会复发。
- 不选原因:本次供应商页踩坑即此盲区直接后果。

### B. STEP 1 全系统一刀切验收(必须 100% 迁完才碰 STEP 2)
- 优点:基线最干净。
- 缺点:大系统 STEP 1 周期极长;期间功能需求积压,反而逼出「赶功能在半成品上盖」。
- 不选原因:模块级切片解锁兼顾基线纪律与产品节奏。

### C. 迁移允许新建页面替换半成品源页
- 优点:不受老骨架牵制。
- 缺点:与「迁移 = 等价」矛盾;易演变为借迁移之名重写,丢失源功能。
- 不选原因:默认增强、禁造新;半成品走「补完 / 登记欠债」而非新建替换。
